Qwen text-to-SQL · Week 4 of 5

The Qwen SQL Gateway

We wrapped the small SQL-writing model from Weeks 1–3 in a "front desk" that decides who gets served, packed everything into containers, watched it with live dashboards, and broke it on purpose to make sure it fails safely.

Terms with a dotted underline link to the glossary at the bottom. Hover (or long-press) for a one-line definition.

The short version

  • The front desk is free. Sending a request through our gateway instead of straight to the model added −1.6 ms (zero, within noise) to a request that takes seconds.
  • Saying "busy, try again" is better than making everyone wait. At 3× more traffic than the machine can handle, refusing extra requests quickly (429) kept the typical wait at 7.3 s. Accepting everything made the typical wait 100 s. The machine did the same amount of work in both cases.
  • It survives being broken. We killed the model mid-answer, crashed it, sent giant inputs, hung up mid-request and shut the gateway down mid-request. In every case users got a clear answer or error, and it recovered on its own (a crash: back in 8.8 s).
  • Testing found one real bug. If a user gave up waiting, the model kept working on their abandoned answer for 27 s while everyone behind them waited. Fixed: now it stops in 0.09 s.
  • Ready for Week 5. The same containers will run in the cloud. One cloud machine should serve roughly 12–18 questions a minute (Week 3 measurement), and we add machines for more.

The system in one picture

A user sends a database description (the schema) and a question in English. The gateway runs four checks, then hands the request to the model server, which writes SQL. Two monitoring tools watch everything. All of it runs as separate containers started together by Docker Compose.

One analogy runs through this page: the model is a kitchen with one chef, the gateway is the host at the door, and the queue is a bench with two seats.

What we did, step by step

  1. Started from Week 3's decision. Week 3 shrank the model 3.1× into a GGUF file (Q4_K_M, 1.0 GB, no measurable accuracy loss) and found that one 4-CPU machine can only usefully work on one request at a time. So our model server, llama-server, runs with a single slot.
  2. Built the gateway. A small Python web service (FastAPI) that every request passes through. It checks the API key, applies a per-client rate limit, rejects oversized input, and manages a short queue. When the queue is full it answers "busy, retry in N seconds" (429) instead of letting requests pile up. This is called back-pressure.
  3. Gave it a product endpoint. /v1/sql takes a schema and a question and returns just the SQL. It builds the prompt exactly the way the model was trained, and a test checks this byte by byte.
  4. Added health signals and logs. /health says the program is alive; /ready says it can actually serve. Every request gets a request id and one structured log line.
  5. Packed it into containers. One image for the gateway (223 MB, runs without admin rights), the official llama.cpp image for the model, plus Prometheus and Grafana. One command starts all four.
  6. Load-tested it with real questions from the Spider benchmark, and ran every returned query to check it was still correct.
  7. Broke it on purpose five ways (failure drills), found one bug, fixed it, re-tested.
  8. Added automatic checks (CI): every code change now builds the gateway image and checks it starts, refuses requests without a key, and reports "not ready" with no model behind it.
What we skipped to finish in time, and why

A GPU version (the deployment has no GPU), comparing several model engines (same reason), automatic switch-over to a backup model server (failover: with one model per machine, adding machines does that job), a separate load-testing tool (our own script also checks SQL correctness), and image security scanning plus publishing (moved to Week 5, when an image actually ships).

Results, explained

Read this first: where the numbers come from. Everything ran on this laptop (a 15-watt Intel i5 with 7.6 GB of RAM that was nearly full). Bug found, then fixed

A user who gives up

26.8 s → 0.09 s
What happened
A user sent a normal (not streaming) request and gave up after 1 s. The model kept writing their answer for 26.8 s more. With one slot, everyone in the queue waited for an answer nobody would read.
Fix
The gateway now watches whether the user is still connected. If they leave, it cancels the model's work and logs code 499. The slot is free in 0.09 s.
In production
Impatient users and mobile apps that lose signal no longer slow everyone else down.

The main experiment: too much traffic, with and without back-pressure

We sent requests at random moments, averaging 0.3 per second for 2 minutes (open loop, Poisson arrivals). That's about 3× what this laptop can serve. Both runs got the exact same 41 requests at the exact same times. The only difference: whether the gateway was allowed to say "busy".

Got an answer16 of 41. The other 25 were told "busy, retry" within 6 s (13 instantly: bench full; 12 after waiting 6 s)41 of 41
Useful answers (within 10 s / 20 s)11 / 152 / 3

Test length124 s349 s (4 more minutes to empty the line)

What it means. An overloaded machine finishes the same number of answers per minute no matter what. Back-pressure doesn't make it faster; it decides who waits. Without it, everyone waits about 100 seconds. Almost nobody keeps a page open that long, so "41 of 41 answered" is really "2 of 41 useful". With it, 15 people got a useful answer, and 25 got a fast, honest "come back in a few seconds" that their app can act on, and that tells the cloud to add machines.

The weak spot. Accepted requests can still wait up to 6 s on the bench and then take up to ~13 s to cook here, hence the 18.5 s p95. On the faster cloud machine, cooking takes ~4–9 s, so a 6 s wait could still push some answers past 10 s. Plan for Week 5: set the maximum wait to about 10 s minus the typical cooking time (≈ 5 s), once we measure the real machine.

How sure are we? Each run happened once, with 41 requests. The gap (7 s vs 100 s) is so large that luck can't explain it, but the exact numbers would shift a little on a rerun.

What this means in production

What a user experiences

A question about a database the system has seen recently comes back in a couple of seconds. A new database takes longer (Week 3's cloud-like machine: ~4 s typical, ~9 s slow end). When it's busy, the user's app hears "retry in N seconds" within 6 s instead of hanging for minutes. If the model crashes mid-answer, the app gets a clear error, not a silently cut-off query.

How it scales (estimate)

Week 3 measured about 0.2–0.3 answers per second per 4-CPU machine, i.e. 12–18 a minute. Batching more requests together on a CPU didn't help, so the way to grow is more machines, each serving one request at a time. Assumption, to be checked in Week 5: the cloud machine performs like Week 3's. Then 100 questions a minute at peak needs roughly 6–8 machines, and the cloud can add them automatically (autoscaling), with a rising 429 rate as one of the signals.

What it costs (estimate)

Week 3 estimated $0.36–0.51 per 1,000 questions on a 4-CPU cloud machine, at an assumed ~$0.38 per machine-hour. Week 5 replaces this with the real bill. The gateway adds no measurable cost.

What breaks first, and how it reacts

The single model slot. When traffic exceeds it, the bench fills, then the gateway refuses politely. Memory is the next risk on small machines (we had to shrink the prompt cache to fit this laptop). If the model process dies, /ready flips to "not ready" in a fraction of a second, so a load balancer stops sending traffic, and Docker or the cloud restarts it (~9 s).

What the engineer on call watches

The Grafana dashboard: the slow-end time (p95) against the 10 s line, requests per second by result code, how many are waiting, refusals by reason, model errors, and whether the service is ready. A rising queue_full count means "add machines". Any mid_stream errors (the model died while answering) mean the model server is crashing.

Decisions this drives

Keep one request at the model per machine. Scale by adding machines. Tune the maximum wait to ~5 s once the cloud machine is measured. Deploy these exact containers in Week 5.

Glossary

Grouped by topic, in reading order: each entry only uses terms from entries above it.

1 · The model and how it answers

Token

A word piece: the unit a language model reads and writes.

Intuition"SELECT count(*)" is a few tokens; a long word can be 2–3. Models count everything in tokens, like a taxi meter counts distance.

HereA typical Spider prompt is ~300 tokens; the SQL answer ~25.

Why it mattersSpeed, memory and cost all scale with tokens.

Prompt

Everything the model is given to read before it answers.

HereFixed instructions + the schema + the question, in the exact layout used in training.

Why it mattersA prompt that differs from training quietly costs accuracy, so a test checks the gateway's prompt byte by byte.

Schema

The list of a database's tables and columns.

HereThe user sends it as CREATE TABLE ... text. It's most of the prompt, and the same for every question about that database.

Prefill

The model reading the prompt before writing the first word.

IntuitionThe chef reading the full order before cooking.

HereOn CPU it's most of a request: ~300 tokens to read vs ~25 to write. Week 3: ~4.6 s of reading vs ~1.1 s of writing.

Not to be confused withDecode, the writing part.

Decode

The model writing its answer, one token at a time.

Here9.3 tokens/s on this laptop, 24 on Week 3's machine.

Tokens per second (tok/s)

How fast the model reads (prefill) or writes (decode).

HereLaptop: 22 read / 9.3 write. Week 3: 66 / 24. That's why this laptop is ~2.5–3× slower.

Quantization

Storing the model's numbers with fewer bits so it's smaller and faster.

IntuitionSame idea as the INT8 ONNX models you deploy at work: round each weight to a coarser grid and accept a tiny error.

HereWeek 3: 16-bit → mostly 4-bit, 3.2 GB → 1.0 GB, accuracy change −0.4 points (could easily be luck).

GGUF

A single-file model format made for running on ordinary CPUs.

Hereqwen3-1.7b-spider-Q4_K_M.gguf, 1.0 GB, the file we deploy.

Why it mattersFree cloud machines have no GPU; GGUF runs fine without one.

Q4_K_M

Q = quantized · 4 = about 4 bits per weight · K = "k-quant" method · M = medium size/quality mix

The specific 4-bit compression recipe we chose for the GGUF file.

HereMost weights at 4 bits, the most sensitive ones at 6. Beat the other 4-bit methods in Week 3 with no measurable loss.

llama.cpp

An open-source C++ engine for running language models on CPUs.

HerePinned build b11610 (Week 3 used b11600, which has no ready-made container; b11610 is 10 changes later).

llama-server

llama.cpp's web server: loads the model file and answers requests.

IntuitionThe kitchen.

HereRuns with 1 slot, 2,048-token limit per request, a prompt cache, and its own metrics.

Slot

A seat at the model: one request it's working on right now.

IntuitionOne chef cooking one order.

Here1 slot. Week 3: 4 slots gave no extra speed on CPU, only made everyone finish later.

Context size

The most tokens (prompt + answer) one request may use.

Here2,048. A 7,799-token prompt was refused in 13 ms with "exceeds context size".

Prompt cache

The model remembers prompts it already read, so it can skip re-reading the shared part.

IntuitionA chef who already knows a regular's usual order only needs to hear what's different.

HereQuestions about an already-seen database: 2.3 s typical vs 11.1 s. The "host RAM" cache (1 GB planned, 256 MB on this laptop) keeps more schemas around.

Why it mattersThe single biggest speed lever on CPU.

Text-to-SQL

Turning an English question into a database query.

Here"How many singers?" → SELECT count(*) FROM singer.

Spider

A public benchmark of English questions with correct SQL, over 200 small databases.

HereOur load tests use its 1,034 "dev" questions, in random order.

Execution accuracy

Share of generated queries that return the right rows when actually run.

HereWeek 3, all 1,034 questions: 64.3%. Week 4 load tests: 82.5–90% on 40-question samples (too small to compare).

2 · Measuring speed

Latency (end-to-end, e2e)

How long one user waits, from sending to getting the full answer.

Here2–32 s on this laptop.

Not to be confused withThroughput, which is about many users.

p50 (median)

The middle wait: half of requests were faster.

Here8.5 s at one-at-a-time; 7.3 s vs 100 s in the overload test.

p95

95th percentile

The slow end: 95% of requests were faster than this; 1 in 20 was slower.

IntuitionThe average hides unhappy users; p95 shows them.

Here19.2 s at one-at-a-time on this laptop; Week 3's machine: 8.6 s.

SLO

Service Level Objective

The speed promise we set ourselves.

Here95% of SQL answers within 10 s (about how long someone waits for a query before giving up).

Not to be confused withSLA, a contract with penalties. An SLO is internal.

Throughput (req/s)

How many requests the system finishes per second.

Here0.10/s here (6 a minute); Week 3's machine 0.21–0.30/s.

Goodput

Throughput counting only successful answers.

Here0.13/s with back-pressure, 0.12/s without: the same work, divided differently.

TTFT

Time To First Token

How long until the first word of a streamed answer appears.

HereRecorded by the gateway for streamed requests. For SQL it matters less: a query is only useful once complete.

Concurrency

How many requests are in progress at the same moment ("c=1" means one at a time).

Closed-loop test

A load test that keeps a fixed number of requests in progress, sending the next only when one finishes.

HereUsed to measure capacity (40 questions, 1 at a time).

Open-loop test

A load test where requests arrive on their own schedule, whether or not earlier ones finished.

IntuitionReal customers don't wait for the previous customer to leave before walking in.

HereThe overload test. Only open loop shows queues building up.

Poisson arrivals

Random arrival times with a steady average rate.

Here0.3 per second on average, with natural clumps and gaps. A fixed random seed gave both runs identical arrivals.

Noise

Random variation between identical runs.

HereWhy −1.6 ms means "zero", and why 40 questions can't confirm an accuracy change.

3 · The gateway (the host at the door)

Gateway

A program in front of the model that checks, queues and forwards every request.

IntuitionThe restaurant host: checks the reservation, controls the line, seats people when the chef is free.

HereAbout 400 lines of Python. Adds no measurable delay.

Backend

The server behind the gateway that does the real work.

Herellama-server.

Endpoint (route)

One URL path the service answers on.

Here/v1/sql (the product), /v1/completions and /v1/chat/completions (raw model access in the common "OpenAI-compatible" format), /health, /ready, /metrics.

FastAPI

A Python library for building web services.

HereThe gateway is written with it and run by uvicorn, the program that actually listens for connections.

HTTP status code

A 3-digit number on every web response saying how it went.

Here2xx = success, 4xx = the caller's problem, 5xx = our problem. Entries below cover the ones we use.

API key (auth)

A secret password that identifies a client program.

HereSent in a header. Missing or wrong → 401. Logs record only a short fingerprint (the first 8 characters of a SHA-256 hash), never the key.

Rate limit

A cap on how often one client may send requests.

Intuition"Max 5 orders at once per table."

HerePer API key: bursts of 5, then 1 per second.

Not to be confused withAdmission control, which protects the model from all clients combined.

Token bucket

A rate-limit method: a jar of tickets that refills at a fixed speed; each request takes one.

IntuitionJar holds 5 tickets, refills 1 per second. 5 requests at once pass; the 6th is told "retry in 1 s".

Not to be confused withThe model's tokens (word pieces). Same word, unrelated.

Queue

The waiting line in front of the model.

IntuitionA bench with 2 seats. If the bench is full, the host turns you away.

HereUp to 2 waiting, each for at most 6 s.

Admission control (in-flight)

Deciding how many requests may be at the model at once ("in flight") and who may wait.

Here1 in flight, 2 waiting. Chosen because Week 3 showed CPU gains nothing from more at once.

Back-pressure

When the system is full, push "slow down" back to the senders instead of storing unlimited work.

IntuitionA pipe valve that closes upstream when the tank is full, instead of the tank bursting.

HereOverload test: typical wait 7.3 s with it, 100 s without.

429 Too Many Requests (+ Retry-After)

"Too busy right now, come back in N seconds."

HereThree reasons: rate_limited (you sent too fast), queue_full (bench full, told instantly), queue_timeout (waited 6 s, no seat freed). The Retry-After header gives the seconds.

Why it mattersClient apps can back off automatically; the cloud can scale on it.

413 Too Large

"Your request is too big."

HereInput over 8,000 characters (≈ the 2,048-token limit), refused in 12 ms before the model sees it.

Timeout (504)

Give up if the model takes too long, and say so.

Here60 s limit → 504 "model took too long".

502 Bad Gateway

"The server behind me isn't answering."

HereReturned when llama-server is down or restarting.

499 Client Closed Request

"The caller hung up before we answered." Not an official code; a widely used logging convention.

HereLogged when we cancel the model's work for a user who left.

Streaming (SSE)

SSE = Server-Sent Events

Sending the answer piece by piece as it's written, instead of all at the end.

HereSupported on the raw endpoints. If the model dies mid-stream, the "200 OK" has already been sent, so the gateway adds an error message inside the stream.

Keep-alive connection, retry

Reusing an open network connection for several requests to save setup time.

HereWeek 3 saw llama-server sometimes close a reused connection just as it was used. The gateway retries once, but only if no reply byte had arrived, so nothing can be generated twice.

Request id

A unique tag that follows one request through every log line and back to the caller.

HereReturned as the x-request-id header. A user can quote it; you find their exact log line.

Structured (JSON) logs

Log lines written as named data fields instead of free text.

Here{"path": "/v1/sql", "status": 200, "latency_ms": 572.6, "key": "ed5a18fb", ...}. Easy to search and count in cloud logging tools.

Failover

Switching to a backup server when the main one fails.

HereSkipped: each machine has one model, and the cloud's load balancer skips unready machines, which does the same job.

4 · Health, crashes and shutdown

Liveness check (/health)

"Is the program alive?" If not, restart it.

HereNever touches the model, so a slow model load doesn't get the gateway killed in a loop.

Readiness check (/ready)

"Can it serve right now?" If not, stop sending it traffic, but don't restart it.

HereAsks llama-server if the model is loaded. Flipped to "not ready" 0.05–0.06 s after the model died.

Not to be confused withLiveness. Mixing them up is a classic outage cause.

SIGTERM

A polite "please shut down" signal a program can react to.

HereWhat Docker and the cloud send before stopping a container.

SIGKILL

An instant, unstoppable kill. The program can't clean up.

HereLike an out-of-memory (OOM) kill, when the system runs out of RAM. Our mid-answer kill drill used it.

Graceful shutdown (drain)

On SIGTERM: stop taking new requests, finish the ones in progress, then exit.

IntuitionLast orders: no new customers, but everyone seated gets their meal.

HereUp to 30 s of drain; Docker waits 35 s before forcing a kill. The drill's in-progress request finished 4.8 s after SIGTERM.

Restart policy

Docker's rule for restarting a container that stops by itself.

Hereunless-stopped: a crash is restarted (back in 8.8 s); a deliberate kill or stop by an operator is not.

5 · Packaging and monitoring

Container (Docker)

A sealed box holding a program plus everything it needs, so it runs the same on any machine.

IntuitionA shipping container: the crane doesn't care what's inside.

Image

The frozen recipe a container starts from.

HereGateway image: 223 MB, built in two stages (build tools stay out of the final image) and runs as a normal user, not admin ("non-root"), which limits damage if it's ever hacked.

Docker Compose

A tool that starts several containers together from one file.

Hereserving/compose.yml: gateway, llama-server, Prometheus, Grafana.

Healthcheck (Docker)

A command Docker runs every few seconds to see if a container is healthy.

HereThe gateway waits for llama-server's healthcheck to pass before starting.

Metrics (counter, gauge, histogram)

Numbers a service exposes about itself. Counter: only goes up (requests served). Gauge: goes up and down (people waiting). Histogram: counts requests per time range, so p50/p95 can be computed.

HereServed at /metrics by the gateway and by llama-server.

Prometheus

A tool that collects metrics from services every few seconds and stores them over time.

HereEvery 5 s, from the gateway and llama-server.

Grafana

A tool that turns stored metrics into live charts.

HereDashboard "Qwen SQL gateway", 8 panels, set up automatically. Every chart query was checked against live data.

CI

Continuous Integration

Automatic tests that run on every code change (here: GitHub Actions).

HereRuns 79 tests, builds the gateway image and checks it behaves (alive, not ready without a model, refuses missing keys, non-root).

Autoscaling (horizontal scaling)

The cloud adding or removing whole machines as traffic changes.

HereOur only way to grow, since one CPU machine handles one request at a time. Week 5 sets it up (Cloud Run on Google Cloud; EC2 is the AWS virtual machine).

Say it in 30 seconds

"I put a 4-bit text-to-SQL model behind a FastAPI gateway with API keys, per-client rate limits and a short queue that answers 429 with a retry time when full. Under three times more traffic than one machine can handle, that kept the typical wait at 7 seconds instead of 100, at the same throughput. I containerized it with Prometheus and Grafana and ran failure drills: model killed mid-answer, crash and auto-restart, oversized prompts, users hanging up, and graceful shutdown. One drill found that abandoned requests blocked the only model slot for 27 seconds, and I fixed it."

Caveats

  • All times come from a slow, memory-starved laptop, about 2.5–3× slower than the planned cloud machine. Week 5 measures the real one.
  • The prompt cache was 256 MB, not the planned 1 GB, so cache hits were rarer than they'll be in the cloud.
  • Each experiment ran once. The big gaps (7 s vs 100 s; 27 s vs 0.09 s) are far beyond noise; small numbers would move a little on a rerun.
  • Accuracy here is from 40-question samples (±12 points of luck). The trustworthy accuracy figure is still Week 3's 64.3% on all 1,034 questions.
  • Unlike Weeks 2–3, we didn't write down predictions before running these tests.
  • Cloud Run gives a container only 10 s to shut down, not 35 s. That covers a normal request (~4–9 s there) but not a slow one.
  • Scaling and cost figures in "production" are estimates built on Week 3's measurements and an assumed price.
